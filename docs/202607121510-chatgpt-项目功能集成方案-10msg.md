# 结论

可以加，而且两个项目的结构比较适合这样二开。最稳妥的架构是：

**`AIComicBuilder（漫画生成项目）` → `pixelle（本地媒体供应商协议）` → `Pixelle-Video（短视频生成项目）` 接口服务 → `ComfyKit（工作流封装工具）` → `ComfyUI（本地节点式工作流引擎）`**

不要把 `Pixelle-Video（短视频生成项目）` 的前端和整套“脚本生成—分镜—成片”流程直接搬进 `AIComicBuilder（漫画生成项目）`。应该保留 `AIComicBuilder（漫画生成项目）` 负责剧本、角色、分镜、关键帧、视频组装，把 `Pixelle-Video（短视频生成项目）` 当成一个独立的本地图像、视频和语音生成网关。

这样改动最小，也不会让两个项目以后难以同步升级。

`AIComicBuilder（漫画生成项目）` 已经有图像供应商、视频供应商、供应商工厂和任务队列；关键帧生成会传角色参考图，视频生成会传首帧、尾帧或者初始图。`Pixelle-Video（短视频生成项目）` 的媒体服务则已经封装了本地工作流、云端工作流和扩展参数传递，因此正好适合作为执行层。

# 一、为什么需要增加一层“桥接接口”

不能直接把 `AIComicBuilder（漫画生成项目）` 对接到 `Pixelle-Video（短视频生成项目）` 现有的公开接口，原因是两边的粒度不一致：

-   `AIComicBuilder（漫画生成项目）` 的图像生成需要角色参考图、参考图标签等信息。
    
-   它的视频生成支持初始图模式，以及首帧加尾帧模式。
    
-   `Pixelle-Video（短视频生成项目）` 当前公开的图像接口主要接收提示词、宽度、高度和工作流。
    
-   它当前公开的视频异步接口更偏向“输入一段内容，生成完整短视频”，会自己完成场景拆分、图片、视频、语音和合成，不是单个漫画镜头的视频生成接口。
    

因此，你需要在 `Pixelle-Video（短视频生成项目）` 里面增加一个专门供漫画项目调用的桥接接口，而不是直接调用整片视频接口。

# 二、推荐的整体调用流程

以生成一个镜头视频为例：

1.  `AIComicBuilder（漫画生成项目）` 创建现有的视频生成任务。
    
2.  视频任务处理器找到 `pixelle（本地媒体供应商协议）`。
    
3.  供应商把提示词、首帧、尾帧、时长、比例和工作流名称发送给桥接接口。
    
4.  桥接接口保存上传图片，并将参数传给 `ComfyKit（工作流封装工具）`。
    
5.  `ComfyKit（工作流封装工具）` 调用本地 `ComfyUI（本地节点式工作流引擎）`。
    
6.  桥接接口返回任务编号。
    
7.  `AIComicBuilder（漫画生成项目）` 轮询任务状态。
    
8.  生成完成后，把视频下载或复制到 `AIComicBuilder（漫画生成项目）` 自己的上传目录。
    
9.  最终由原来的漫画视频组装流程继续处理。
    

这里建议始终让 `AIComicBuilder（漫画生成项目）` 的任务表作为外层状态来源，不要让业务状态完全依赖本地生成服务。

# 五、最关键的一步：工作流参数规范

仅仅“能读取工作流文件”还不够。不同 `ComfyUI（本地节点式工作流引擎）` 工作流的节点编号不同，不能在 `TypeScript（类型脚本语言）` 代码里写死某个节点编号。

正确做法是为每个工作流建立稳定的参数契约。

## 图像工作流至少约定

-   `prompt（提示词）`
    
-   `negative_prompt（负面提示词）`
    
-   `width（宽度）`
    
-   `height（高度）`
    
-   `seed（随机种子）`
    
-   `steps（采样步数）`
    
-   `image_path（输入图片路径）`
    
-   `reference_images（参考图片集合）`
    

## 视频工作流至少约定

-   `prompt（提示词）`
    
-   `image_path（初始图片路径）`
    
-   `first_frame（首帧路径）`
    
-   `last_frame（尾帧路径）`
    
-   `duration（时长）`
    
-   `width（宽度）`
    
-   `height（高度）`
    
-   `fps（帧率）`
    
-   `seed（随机种子）`
    

`Pixelle-Video（短视频生成项目）` 的工作流已经通过节点元数据标题使用类似 `$prompt.value!（必填提示词占位符）`、`$width.value（宽度占位符）` 和 `$height.value（高度占位符）` 的参数机制，所以应继续沿用这一套方式，而不是依赖节点编号。

建议每个自定义工作流旁边再放一个能力清单，例如：

`workflow-name.meta.json（工作流能力清单文件）`

其中描述：

-   工作流类型
    
-   必填参数
    
-   可选参数
    
-   是否支持参考图
    
-   最多支持多少张参考图
    
-   是否支持初始图
    
-   是否支持首尾帧
    
-   支持的画面比例
    
-   输出是图片还是视频
    
-   推荐默认值
    

这样设置界面就能只展示符合当前任务要求的工作流。例如，执行首尾帧视频任务时，不应该让用户选择只支持单张初始图的视频工作流。

# 六、任务队列和数据库怎么处理

第一版通常不需要增加新表。

`AIComicBuilder（漫画生成项目）` 当前任务结构已经有：

-   待处理、执行中、已完成、失败等状态
    
-   任务参数
    
-   执行结果
    
-   重试次数
    
-   图像生成任务
    
-   视频生成任务
    
-   视频组装任务
    

镜头资源记录也已经可以保存供应商、模型编号和扩展元数据。

建议在现有任务结果或镜头资源元数据里增加：

-   本地工作流键
    
-   本地生成任务编号
    
-   `ComfyUI（本地节点式工作流引擎）` 任务编号
    
-   实际随机种子
    
-   实际采样参数
    
-   结果原始地址
    
-   结果本地地址
    
-   执行耗时
    
-   失败原因
    

任务执行模式建议是：

**漫画任务队列是外层任务，媒体网关任务是内层任务。**

外层任务提交内层任务并轮询。发生重试时使用漫画任务编号作为幂等标识，避免网络中断后重复提交两次相同的视频生成任务。

本地 `GPU（图形处理器）` 并发建议默认设为一，可以在供应商设置里增加“最大并发任务数”。图像和视频也最好分开设置并发量。

# 七、容器部署建议

推荐三个服务：

-   `AIComicBuilder（漫画生成项目）`：主应用
    
-   `Pixelle-Video（短视频生成项目）`：本地媒体网关
    
-   `ComfyUI（本地节点式工作流引擎）`：实际模型执行服务
    

在同一个 `Docker（容器工具）` 网络中，可以使用：

-   `http://pixelle:8000（容器内媒体网关地址）`
    
-   `http://comfyui:8188（容器内工作流引擎地址）`
    

如果 `ComfyUI（本地节点式工作流引擎）` 运行在宿主机，而 `Pixelle-Video（短视频生成项目）` 运行在容器内，不能把地址写成 `127.0.0.1（本机回环地址）`，因为它会指向容器本身。项目配置说明中也明确给出了：苹果和微软系统可以使用 `host.docker.internal（容器访问宿主机地址）`，`Linux（类尤尼克斯系统）` 通常需要使用宿主机实际地址。

不要把 `8188（工作流引擎端口）` 直接暴露到公网。建议只有媒体网关能访问它。

# 八、安全上必须补的内容

即使主要是本地使用，也建议处理这些问题：

-   所有本地工作流调用都从服务端发起，不让浏览器直接访问 `ComfyUI（本地节点式工作流引擎）`
    
-   限制可配置的基础地址，避免 `SSRF（服务端请求伪造）`
    
-   检查图片和视频的 `MIME（媒体类型标识）`
    
-   限制上传文件大小
    
-   清理文件名，阻止目录穿越
    
-   临时文件定期删除
    
-   输出路径必须位于允许的目录中
    
-   跨机器部署时给媒体网关增加访问令牌
    
-   不把本机绝对路径返回给浏览器
    
-   对长时间视频任务设置超时、取消和失败重试
    

这样也能避免浏览器跨域问题，不需要让 `ComfyUI（本地节点式工作流引擎）` 自己处理 `CORS（跨域资源共享）`。

# 九、哪些 `Pixelle-Video（短视频生成项目）` 功能值得迁移

→ 混合旁白、字幕和背景音乐

→ 输出最终视频。

这与 `Pixelle（自动短视频项目）` 的“主题—文案—配图—语音—背景音乐—视频”产品逻辑一致，但代码、数据库和界面都由 `AIComicBuilder（人工智能漫画构建器）` 重新实现。`Pixelle（自动短视频项目）` 官方当前也把图片、视频和语音设计成可替换的原子能力，并支持通过 `ComfyUI（本地工作流引擎）` 执行。

# 二、建议使用两个本地 `ComfyUI（本地工作流引擎）` 实例

技术上可以把 `Z-Image（造相文生图模型）` 和 `IndexTTS2（零样本声音克隆模型）` 都安装进同一个实例，但正式使用时，我更建议分开：

-   `http://127.0.0.1:8188`（本地图像工作流地址）
    
-   `http://127.0.0.1:8190`（本地语音工作流地址）
    

两个实例仍然可以使用同一张 `GPU（图形处理器）`，只是由主项目控制任务顺序。

这样做有几个好处：

1.  图像节点与语音节点的依赖环境互不影响。
    
2.  更新语音节点不会破坏图像环境。
    
3.  某个实例崩溃，不会同时影响图像和语音。
    
4.  可以分别配置模型释放、超时和并发数。
    
5.  将来有两张显卡时，可以直接把两个实例分配到不同显卡。
    

默认建议把本地推理并发数设为一。即使电脑显存较高，也先避免同时加载 `Z-Image（造相文生图模型）` 和 `IndexTTS2（零样本声音克隆模型）`。后续确认显存余量后，再开放图像和语音并行。

# 三、不要把声音克隆硬塞进现有模型供应商接口

`AIComicBuilder（人工智能漫画构建器）` 当前的 `AIProvider（人工智能供应商接口）` 只有文本和图片生成方法，视频使用单独的 `VideoProvider（视频供应商接口）`，并没有音频生成能力。现有供应商工厂也主要面向云端模型协议。

因此第一版不建议直接修改现有的：

`src/lib/ai/provider-factory.ts`（人工智能供应商工厂文件）

更合理的是新增一个通用本地工作流层：

```
src/lib/comfyui/client.ts（本地工作流客户端）
src/lib/comfyui/runner.ts（本地工作流执行器）
src/lib/comfyui/registry.ts（工作流注册表）
src/lib/comfyui/types.ts（工作流类型定义）
```

然后在短视频领域中增加两个服务：

```
src/lib/short-video/services/z-image-service.ts（造相配图服务）
src/lib/short-video/services/index-tts2-service.ts（声音克隆服务）
```

业务层只调用：

-   `generateImage（生成图片）`
    
-   `generateVoice（生成旁白）`
    

至于底层工作流用了哪些节点、节点编号是多少，全部交给工作流配置层处理。

这样将来从 `IndexTTS2（零样本声音克隆模型）` 升级到其他语音模型，或者从 `Z-Image（造相文生图模型）` 更换为其他文生图模型，不需要改短视频业务代码。

# 四、通用 `ComfyUI（本地工作流引擎）` 执行器怎么设计

本地工作流执行器需要实现以下能力：

-   检测服务是否可用；
    
-   读取工作流接口文件；
    
-   按参数映射修改工作流；
    
-   提交任务；
    
-   保存返回的任务编号；
    
-   接收执行进度；
    
-   查询执行历史；
    
-   获取输出文件；
    
-   取消任务；
    
-   处理超时；
    
-   在应用重启后恢复查询。
    

`ComfyUI（本地工作流引擎）` 官方服务支持通过 `/prompt（工作流提交接口）` 提交任务，通过 `/ws（实时通信接口）` 获取进度，通过 `/history/{prompt_id}（任务历史接口）` 查询结果，也支持 `/interrupt（任务中断接口）`。官方建议使用“实时通信加历史查询”的方式等待任务完成。

工作流必须从界面中导出为 `API（应用程序接口）` 格式，而不是普通保存格式。官方文档明确区分了普通界面保存文件和接口提交文件，接口格式以节点编号为键，不包含画布位置等界面信息。

## 工作流文件建议这样存放

```
data/workflows/z-image-turbo.api.json（造相快速工作流接口文件）
data/workflows/z-image-base.api.json（造相质量工作流接口文件）
data/workflows/index-tts2.api.json（声音克隆工作流接口文件）

data/workflows/z-image-turbo.manifest.json（造相快速工作流参数映射）
data/workflows/z-image-base.manifest.json（造相质量工作流参数映射）
data/workflows/index-tts2.manifest.json（声音克隆工作流参数映射）
```

参数映射文件负责描述：

| 业务参数 | 对应工作流参数 |
| --- | --- |
| `prompt（提示词）` | 正向提示词节点的文本输入 |
| `negativePrompt（负面提示词）` | 负向提示词节点的文本输入 |
| `width（宽度）` | 潜空间节点宽度 |
| `height（高度）` | 潜空间节点高度 |
| `seed（随机种子）` | 采样节点随机种子 |
| `steps（采样步数）` | 采样节点步数 |
| `speakerAudio（音色参考音频）` | 音频加载节点输入 |
| `emotionAudio（情绪参考音频）` | 情绪音频节点输入 |
| `emotionStrength（情绪强度）` | 情绪影响强度 |
| `text（旁白文本）` | 语音生成节点文本输入 |

节点编号只存在参数映射文件中，不能散落在短视频业务代码里。每次修改工作流后，工作流文件和参数映射文件一起升级版本。

# 五、数据库不要复用漫剧的镜头和对白表

`AIComicBuilder（人工智能漫画构建器）` 当前项目表和镜头、对白、角色、分镜资源表都是围绕漫剧设计的。直接把短视频分段存进 `shots（镜头表）` 和 `dialogues（对白表）`，后续会让两条业务线越来越难维护。

建议只给公共项目表增加一个字段：

```
projectType（项目类型）
```

可选值：

-   `comic（漫剧）`
    
-   `short_video（短视频）`
    

然后新增五张短视频专用表。

## 1\. `short_video_projects（短视频项目扩展表）`

主要字段：

-   项目编号；
    
-   输入模式：主题生成或固定文案；
    
-   主题；
    
-   完整解说稿；
    
-   画面比例；
    
-   输出宽高；
    
-   帧率；
    
-   视觉风格；
    
-   图像工作流编号；
    
-   语音工作流编号；
    
-   声音档案编号；
    
-   背景音乐；
    
-   背景音乐音量；
    
-   字幕样式；
    
-   当前生成阶段。
    

## 2\. `short_video_segments（短视频分段表）`

一个分段代表一段旁白和一个画面。

主要字段：

-   项目编号；
    
-   顺序；
    
-   旁白文本；
    
-   图像提示词；
    
-   负面提示词；
    
-   情绪描述；
    
-   转场类型；
    
-   预计时长；
    
-   实际音频时长；
    
-   当前状态。
    

## 3\. `short_video_assets（短视频资源表）`

保存每个分段生成的文件：

-   图片；
    
-   旁白；
    
-   分段视频；
    
-   字幕；
    
-   最终视频。
    

还需要保存：

-   资源版本；
    
-   是否为当前版本；
    
-   文件地址；
    
-   工作流编号；
    
-   `ComfyUI（本地工作流引擎）` 任务编号；
    
-   随机种子；
    
-   实际生成参数；
    
-   错误信息。
    

这样用户重新生成某一张图片或者某一段旁白时，旧版本不会丢失。

## 4\. `voice_profiles（声音档案表）`

主要字段：

-   声音名称；
    
-   参考音频地址；
    
-   可选情绪音频地址；
    
-   默认情绪强度；
    
-   语言；
    
-   是否已确认拥有声音使用权；
    
-   创建时间。
    

## 5\. `comfy_workflows（本地工作流配置表）`

主要字段：

-   工作流名称；
    
-   类型：图片或语音；
    
-   执行实例地址；
    
-   工作流文件地址；
    
-   参数映射文件地址；
    
-   版本；
    
-   是否启用；
    
-   必需自定义节点；
    
-   最近一次连接检测结果。

# 七、`Z-Image（造相文生图模型）` 的接入建议

不要只配置一个工作流，建议同时准备两个。

## 快速工作流

使用：

`Z-Image-Turbo（造相快速文生图模型）`

适合：

-   批量生成全部分段的第一版配图；
    
-   快速查看整条视频效果；
    
-   频繁重新生成。
    

官方说明中，`Z-Image-Turbo（造相快速文生图模型）` 只需要八次函数评估，并且可以在十六吉字节显存的消费级设备上运行。

## 质量工作流

使用：

`Z-Image（造相基础文生图模型）`

适合：

-   对选中的重要画面进行精修；
    
-   需要更高多样性；
    
-   需要负面提示词；
    
-   需要更强的构图控制；
    
-   后续增加风格微调。
    

官方将基础版本定位为更适合高质量、多样性、可控生成和下游开发的版本，基础版本通常使用更多采样步骤与引导。

所以实际产品可以提供：

-   “快速生成全部配图”
    
-   “使用质量模式重新生成当前配图”
    

这会比所有图片都跑高质量工作流更实用。

`ComfyUI（本地工作流引擎）` 官方模板已经提供 `Z-Image（造相文生图模型）` 工作流，涉及的核心模型文件包括：

-   `qwen_3_4b.safetensors（文本编码器权重）`
    
-   `z_image_bf16.safetensors（造相扩散模型权重）`
    
-   `ae.safetensors（图像编解码器权重）`
    

对应放入文本编码器、扩散模型和图像编解码器目录。

短视频项目每个分段传入：

-   当前分段画面提示词；
    
-   项目级统一风格前缀；
    
-   宽度和高度；
    
-   随机种子；
    
-   工作流模式；
    
-   输出文件名前缀。
    

为了保证整条视频视觉统一，项目级设置中还应保存：

-   统一色调；
    
-   统一画面风格；
    
-   统一镜头语言；
    
-   统一材质描述；
    
-   统一时代和场景描述。
    

单纯固定随机种子不能保证跨画面角色一致。涉及固定人物时，后续需要增加 `LoRA（低秩适配模型）`、参考图或者其他角色一致性工作流。

# 八、`IndexTTS2（零样本声音克隆模型）` 的接入建议

声音档案页面让用户上传一份参考声音，然后保存为可复用声音档案。

每个分段执行语音工作流时传入：

-   旁白文本；
    
-   音色参考音频；
    
-   可选情绪参考音频；
    
-   情绪强度；
    
-   随机策略；
    
-   输出文件名。
    

`IndexTTS2（零样本声音克隆模型）` 官方示例支持使用一份参考音频完成声音克隆，也支持另传一份情绪参考音频，并可调整情绪影响强度。

建议默认关闭随机采样，因为官方说明指出随机采样会降低声音克隆相似度。

## 不要一次生成整篇旁白

应该按短视频分段分别生成：

```
第一段旁白 → 第一段音频
第二段旁白 → 第二段音频
第三段旁白 → 第三段音频
```

这样才能做到：

-   单独试听；
    
-   单独重新生成；
    
-   单独调整情绪；
    
-   单独修正读音；
    
-   精确建立字幕时间轴；
    
-   某一段失败时不必重做全文。
    

## 不要依赖精确时长控制

虽然 `IndexTTS2（零样本声音克隆模型）` 的研究设计包含时长控制，但官方公开仓库的发布说明仍明确写着，二〇二五年九月八日发布版本中该功能尚未启用。

因此短视频流程应该这样处理：

1.  先生成旁白；
    
2.  使用 `ffprobe（媒体信息检测工具）` 读取真实音频时长；
    
3.  分段视频时长设置为音频时长加少量停顿；
    
4.  根据累计音频时长生成字幕时间轴；
    
5.  不对声音做大幅加速或者减速；
    
6.  时长差异过大时，优先改写文案并重新生成。
    

这种方式比依赖语音模型的预估时长更稳定。

## `ComfyUI（本地工作流引擎）` 自定义节点

可以先选择一个已经能稳定运行的 `IndexTTS2（零样本声音克隆模型）` 节点作为第一版。例如 `ComfyUI-kaola-IndexTTS2（考拉版声音克隆节点）` 已提供基础声音克隆、音频情绪控制、向量情绪控制、文字情绪控制以及分角色字幕配音，并使用标准音频加载和保存节点。

不过不要让主项目依赖这个节点的类名。主项目只认“音色参考、文本、情绪、输出音频”这些逻辑字段，具体节点映射放在工作流参数映射文件中。以后更换节点，只替换工作流和参数映射。

# 九、声音文件如何传给本地语音实例

最稳妥的是使用共享目录。

例如：

```
AIComicBuilder/uploads/private/voices/（主项目私人声音目录）
ComfyUI-Audio/input/voices/（语音实例输入目录）
ComfyUI-Audio/output/short-video/（语音实例输出目录）
```

流程是：

1.  用户上传参考音频到主项目私人目录；
    
2.  主项目复制一份到语音实例输入目录；
    
3.  音频加载节点读取该文件；
    
4.  语音工作流生成音频；
    
5.  主项目从输出目录复制结果到自己的素材目录；
    
6.  数据库只保存主项目相对文件地址。
    

不要在数据库保存语音实例的绝对磁盘路径，也不要让浏览器直接访问本地工作流实例。

`ComfyUI（本地工作流引擎）` 官方核心上传接口主要提供图片和遮罩上传，因此在同一台电脑部署时，共享目录会比专门增加音频上传接口简单。

# 十、短视频任务链如何接入现有任务队列

新增以下任务类型：

```
short_video_plan（短视频规划任务）
short_video_image（短视频配图任务）
short_video_voice（短视频旁白任务）
short_video_clip（短视频分段渲染任务）
short_video_assemble（短视频成片合成任务）
```

任务执行顺序：

## 1\. `short_video_plan（短视频规划任务）`

-   调用文本模型；
    
-   生成完整解说稿；
    
-   拆分分段；
    
-   生成画面提示词；
    
-   写入分段表；
    
-   为每个分段创建图片和语音任务。
    

## 2\. `short_video_image（短视频配图任务）`

-   读取工作流；
    
-   填入提示词、宽高和随机种子；
    
-   提交到图像实例；
    
-   保存工作流任务编号；
    
-   等待完成；
    
-   复制图片到主项目素材目录；
    
-   写入资源表。
    

## 3\. `short_video_voice（短视频旁白任务）`

-   准备参考音频；
    
-   填入旁白文本和情绪参数；
    
-   提交到语音实例；
    
-   保存工作流任务编号；
    
-   复制生成音频；
    
-   检测实际时长；
    
-   更新分段记录。
    

## 4\. `short_video_clip（短视频分段渲染任务）`

使用 `FFmpeg（音视频处理工具）`：

-   把静态图片转为视频片段；
    
-   添加缓慢缩放和平移；
    
-   时长匹配旁白；
    
-   加入分段旁白；
    
-   生成分段字幕。
    

## 5\. `short_video_assemble（短视频成片合成任务）`

-   按顺序拼接分段；
    
-   添加转场；
    
-   混合背景音乐；

# 十一、现有任务队列还需要补一个重要能力

当前工作器会把任务设置为运行中，然后等待处理器结束。任务失败时可以重试，但是应用进程在任务运行期间直接退出，任务可能一直停留在运行中状态。

新增本地长任务后，建议增加：

-   `externalJobId（外部工作流任务编号）`
    
-   `heartbeatAt（任务心跳时间）`
    
-   `startedAt（任务开始时间）`
    
-   `progress（任务进度）`
    
-   `dedupeKey（任务去重标识）`
    

应用启动时：

1.  查找长时间没有心跳的运行中任务；
    
2.  如果已经有工作流任务编号，先查询本地工作流历史；
    
3.  已完成则恢复结果；
    
4.  仍在执行则继续监控；
    
5.  确认不存在后才重新提交。
    

否则网络中断或者主项目重启后，可能重复生成同一张图或者同一段声音。

-   在首尾帧生成时传入角色参考图；
    
-   在视频生成时传入参考图片。
    

当前角色四视图实际上被生成为一张横向大图，然后存入单个角色参考图字段；首尾帧生成时，会把角色参考图作为普通参考图片数组传给图像供应商。

这些能力对漫剧很合适，但直接用于短视频存在几个问题：

| 当前设计 | 短视频中的问题 |
| --- | --- |
| 角色默认偏向人类 | 动物、卡通形象、机器人、吉祥物不适合“身高、体型、服装”这种固定结构 |
| 一个主要参考图字段 | 不足以表达正面、侧面、脸部、全身、表情、毛色、配饰等多类参考 |
| 角色直接属于漫剧项目 | 不利于跨短视频项目复用 |
| 所有参考图只是普通数组 | 不知道哪张是身份图、风格图、场景图、首帧或尾帧 |
| 当前视频接口只有首尾帧模式和单初始图模式 | 难以完整表达不同云端视频模型的能力差异 |
| 角色描述与生成参数耦合 | 更换 `Z-Image（造相模型）`、`Veo（谷歌视频模型）` 等模型时容易污染业务数据 |

因此，短视频模块中不要继续把它叫“人物管理”，建议改成：

# **视觉主体**

视觉主体可以是：

-   人类；
    
-   动物；
    
-   卡通角色；
    
-   吉祥物；
    
-   怪兽或幻想生物；
    
-   机器人；
    
-   拟人化物品；
    
-   品牌形象；
    
-   需要长期保持外观一致的特殊物件。
    

原来的漫剧页面仍然叫“角色”，短视频页面叫“视觉主体”。二者通过适配层复用数据，不强制共用业务表。

-   文件大小；

-   工作流路径；
    
-   相对路径；
    

纳入资源记录，并明确不把用户机器上的绝对路径写进持久化追踪信息。这一设计应该原样保留。

## 6\. `ZImagePromptBundle（造相提示词包）`

你已经将 `Z-Image（造相模型）` 的输入拆成：

-   正向提示词；
    
-   负向提示词；
    
-   锁定约束；
    
-   追踪元数据。
    

这比把所有内容拼成一条不可解释的提示词可靠得多。

## 7\. `OmniVoiceLongformBlockPlan（全语种声音长文分块计划）`

你现在已经有：

-   原文摘要；
    
-   原文字符位置；
    
-   语义分块；
    
-   分块原因；
    
-   音频路径；
    
-   归一化音频；
    
-   实际时长；
    
-   长文本按句子边界拆分。
    

这些都应该成为 `ai-m（新项目）` 短视频语音模块的基础。

所以最合理的迁移原则是：

> **把 `Pixelle-Video（短视频生成项目）` 的领域契约和质量规则迁移到 `ai-m（新项目）`，不要把大量 `Python（蟒蛇语言）` 服务类逐个翻译成 `TypeScript（类型脚本语言）`。**

建议把当前 `Pixelle-Video（短视频生成项目）` 作为“业务规格参考实现”，而不是作为未来运行时依赖。

# 三、建议确定新的产品北极星

新的产品定位可以写成：

> **面向旁白解说类创作者的本地优先短视频生产平台，通过可复用的视觉主体资产、声音克隆、音频主时间线和可插拔生成模型，稳定生产人物一致、声音一致、音画同步的系列短视频。**

新的北极星指标建议调整为：

> **每周成功导出并通过视觉一致性与音画同步质量门槛的短视频数量。**

不能只统计“生成了多少张图片”或者“调用了多少次模型”。真正要衡量的是完整闭环。

护栏指标建议包括：

| 指标 | 含义 |
| --- | --- |
| 视觉主体一致性通过率 | 同一主体在多个镜头中外观是否稳定 |
| 旁白同步通过率 | 字幕、画面与旁白是否正确对齐 |
| 单镜头重做率 | 有多少镜头需要人工反复生成 |
| 单条视频云端成本 | 使用云端视频模型的实际成本 |
| 本地推理成功率 | `Z-Image（造相模型）` 与声音模型是否稳定执行 |
| 任务恢复率 | 应用重启后是否能恢复长任务 |
| 漫剧回归通过率 | 新功能不能破坏原有漫剧流程 |

# 五、视觉主体应该怎样建模

建议新增短视频专用的视觉主体表，不直接修改原来的 `characters（角色表）`。

## 视觉主体基础信息

建议包含：

| 字段 | 作用 |
| --- | --- |
| 主体类型 | 人类、动物、卡通、吉祥物、机器人等 |
| 显示名称 | 界面中显示的名称 |
| 视觉摘要 | 对主体的一句话总结 |
| 身份锚点 | 最能决定身份的固定特征 |
| 身份锁定 | 每次生成必须保持的属性 |
| 可变槽位 | 允许变化的服装、姿势、表情等 |
| 禁止特征 | 绝对不能出现的错误特征 |
| 渲染风格 | 写实、二维动画、三维卡通、绘本等 |
| 默认色板 | 主体的主要颜色 |
| 连续性说明 | 跨镜头保持一致的特殊要求 |
| 当前版本 | 项目实际锁定的身份版本 |

## 不同类型的身份锁定内容

### 人类

重点锁定：

-   五官；
    
-   发型；
    
-   年龄感；
    
-   肤色；
    
-   身材比例；
    
-   眼睛颜色；
    
-   标志性配饰；
    
-   默认服装；
    
-   脸部特殊特征。
    

### 动物

重点锁定：

-   物种；
    
-   毛色与花纹；
    
-   耳朵形状；
    
-   尾巴形状；
    
-   眼睛颜色；
    
-   体型比例；
    
-   特殊斑纹；
    
-   项圈或其他配饰。
    

动物的一致性不能只依靠人脸识别机制。

### 卡通或吉祥物

重点锁定：

-   头身比例；
    
-   轮廓；
    
-   主色和辅色；
    
-   眼睛形状；
    
-   嘴部结构；
    
-   手脚比例；
    
-   标志性服饰；
    
-   图形符号；
    
-   是否允许写实化；
    
-   是否允许增加真实毛发或皮肤纹理。
    

卡通角色最常见的问题不是“脸变了”，而是：

-   画风突然写实；
    
-   身体比例变化；
    
-   配色漂移；
    
-   配饰消失；
    
-   多出手指、尾巴或耳朵；
    
-   从二维变成三维。
    

因此必须有风格边界和禁止项。

# 七、不要让原漫剧角色和短视频视觉主体双向自动同步

为保持原漫剧流程稳定，建议新增：

`character_visual_entity_links（漫剧角色与视觉主体关联表）`

它只负责建立映射。

第一阶段采用**快照导入**：

1.  用户在漫剧角色页面点击“发布到视觉资产库”；
    
2.  系统读取角色名称、描述、参考图、服装和历史参考图；
    
3.  创建一个独立的视觉主体版本；
    
4.  短视频项目从视觉资产库中选择这个版本；
    
5.  后续修改漫剧角色，不自动影响已经生成的短视频项目。
    

反过来，短视频视觉主体的修改也不自动覆盖漫剧角色。

这样既能复用原有角色能力，又不会因为共享编辑而破坏已完成项目。

以后可以增加“升级到新身份版本”，但必须由用户主动操作。

# 八、短视频需要区分“叙事片段”和“视觉镜头”

这是音画对齐中最重要的数据模型调整。

## 叙事片段

一个叙事片段代表一段完整语义，例如：

> 小猫每天都会站在窗边，等待已经离开的主人回家。

它主要保存：

-   旁白文本；
    
-   情绪；
    
-   发音说明；
    
-   生成音频；
    
-   音频实际时长；
    
-   字幕；
    
-   片段起止时间。
    

## 视觉镜头

一个叙事片段可以对应一个或多个视觉镜头，例如：

1.  小猫蹲在窗台；
    
2.  雨滴滑过玻璃；
    
3.  空荡的房间；
    
4.  小猫回头看向门口。
    

每个视觉镜头保存：

-   所属叙事片段；
    
-   镜头时长；
    
-   视觉主体选角；
    
-   场景与道具；
    
-   静态图片或动态视频模式；
    
-   图像提示词；
    
-   视频运动提示词；
    
-   供应商；
    
-   参考图片；
    
-   当前资源版本。
    

关系应该是：

> **一个叙事片段对应一个或多个视觉镜头。**

不能再默认“一句话等于一张图片”，否则长句旁白会导致一张图停留太久，短句又会导致镜头切换过快。

# 九、本地 `Z-Image（造相模型）` 应该怎样接入

`Z-Image（造相模型）` 官方目前包含快速版、基础版和编辑方向；快速版适合低步骤快速生成，基础版更侧重质量、多样性与可控性。

建议为短视频准备至少三类 `ComfyUI（本地工作流引擎）` 工作流。

## 1\. 快速预览工作流

使用：

`Z-Image-Turbo（造相快速模型）`

用途：

-   一次生成全部镜头初稿；
    
-   检查内容节奏；
    
-   快速确认视觉方向；
    
-   降低反复修改成本。
    

## 2\. 最终质量工作流

使用：

`Z-Image（造相基础模型）`

用途：

-   生成最终图片；
    
-   对重要镜头精修；
    
-   使用负面提示词；
    
-   更精细控制构图与画风。
    

## 3\. 身份参考工作流

用途：

-   注入视觉主体主身份图；
    
-   注入多角度参考图；
    
-   注入风格参考；
    
-   支持局部重绘或编辑；
    
-   尽可能保持主体一致。
    

需要强调：

> **文生图模型本身并不能自动保证多镜头人物一致。**

真正的一致性来自：

-   身份描述锁定；
    
-   主身份图；
    
-   多角度参考图；
    
-   参考图工作流；
    
-   必要时的 `LoRA（低秩适配模型）`；
    
-   适合人类身份的脸部约束；
    
-   适合动物与卡通角色的轮廓、配色、花纹和比例约束；
    
-   生成后的视觉检查和重做。
    

你在 `Pixelle-Video（短视频生成项目）` 中已经有 `off（关闭）`、`auto（自动）`、`required（强制）` 三种参考图注入模式，可以直接把这个思想迁移过来。

每个本地工作流应声明：

-   是否支持参考图；
    
-   是否强制要求参考图；
    
-   最多支持多少张；
    
-   支持哪些参考角色；
    
-   提示词节点；
    
-   负面提示词节点；
    
-   随机种子节点；
    
-   宽高节点；
    
-   输出节点；
    
-   工作流版本；
    
-   必需自定义节点。
    

当镜头存在固定视觉主体，但用户选择的工作流不支持参考图时，系统应提示：

> 当前工作流无法保证视觉主体一致性。

而不是悄悄退化成纯文生图。

# 十、云端视频模型不要用一个通用参数强行兼容

`ai-m（新项目）` 当前视频请求主要是两种模式：

-   首帧加尾帧；
    
-   一张初始图。
    

再附加提示词、时长、比例和普通参考图片数组。现有供应商工厂已经接入了 `Seedance（即梦视频模型）`、`Veo（谷歌视频模型）`、`Kling（可灵视频模型）` 等，但接口仍然明显围绕漫剧首尾帧流程设计。

不要修改这个接口去适配所有短视频模型。

建议另外新增短视频专用的“视频生成契约”，它至少表达：

-   文本生成视频；
    
-   单图生成视频；
    
-   首尾帧生成视频；
    
-   多参考图生成视频；
    
-   风格参考；
    
-   主体参考；
    
-   源视频编辑；
    
-   视频延长；
    
-   是否生成原生声音；
    
-   允许的时长；
    
-   画面比例；
    
-   分辨率；
    
-   随机种子；
    
-   异步任务；
    
-   任务取消；
    
-   成本估算。
    

每个供应商通过“能力声明”告诉系统自己支持哪些功能。

例如，当前 `Veo 3.1（谷歌视频模型三点一版）` 官方接口允许最多三张主体参考图片，并支持首尾帧控制；当前 `Grok Imagine（格罗克视觉生成模型）` 官方接口提供图像生成、最多三张图片的图像编辑，以及从静态图片生成视频的能力。

`Kling（可灵视频模型）` 和 `Seedance（即梦视频模型）` 也应分别通过适配器声明当前版本支持的模式，而不是让业务页面根据供应商名字写判断。`Seedance 2.0（即梦视频模型二点零版）` 已有官方视频生成接口文档，`Kling VIDEO 3.0（可灵视频模型三点零版）` 官方也在持续扩展文本、图片与参考生成能力，因此能力配置必须允许随模型版本更新。

# 十一、保持主体一致的最佳视频路径

对于包含固定人物、动物或卡通主体的镜头，优先路径应该是：

1.  从资产圣经读取主体身份版本；
    
2.  使用本地 `Z-Image（造相模型）` 和参考工作流生成稳定关键帧；
    
3.  对关键帧做视觉一致性检查；
    
4.  把通过检查的关键帧交给云端视频模型；
    
5.  同时传递供应商允许的身份参考图；
    
6.  只让云端模型负责运动，不让它重新设计角色。
    

也就是：

> **本地生成身份稳定的图片，云端负责让这张图片动起来。**

纯文本生成视频主要用于：

-   风景；
    
-   抽象画面；
    
-   城市延时；
    
-   无固定角色的补充画面；
    
-   粒子、宇宙、数据可视化；
    
-   不要求跨镜头一致的场景。
    

包含固定主体时，默认使用图片生成视频。

对于支持首尾帧的供应商，可以由本地生成：

-   起始关键帧；
    
-   结束关键帧；
    

再交给云端模型插值。

# 十二、每个镜头都应该可以独立选择媒体模式

不要给整个项目只设置一个视频模型。

每个视觉镜头可以选择：

| 模式 | 适用情况 |
| --- | --- |
| 本地静态图片 | 知识、历史、情感、故事解说 |
| 本地图片加运动 | 成本低、主体一致性要求高 |
| 云端图片生成视频 | 需要明显动作的角色镜头 |
| 云端文本生成视频 | 无固定主体的补充画面 |
| 首尾帧视频 | 对开始和结束构图有明确要求 |
| 用户上传素材 | 已有实拍或版权素材 |
| 纯文字模板 | 标题、数据和引语画面 |

项目只保存默认策略，镜头允许覆盖。

推荐的默认策略是：

-   大部分镜头使用本地图片；
    
-   通过平移、缩放和景深效果增加动态感；
    
-   只有少数重要镜头使用云端视频；
    
-   固定主体镜头尽量使用图片生成视频；
    
-   无固定主体镜头可以直接文本生成视频。
    

这样可以同时控制成本、一致性和生成时间。

---

# 十三、旁白不应使用云端视频模型自带的对白声音

即使部分视频模型可以生成原生声音，也不建议把它作为旁白来源。

原因是：

-   无法保证跨镜头声音一致；
    
-   无法稳定使用用户克隆音色；
    
-   台词内容容易偏离原文；
    
-   字幕难以精确对应；
    
-   不同镜头的响度和情绪可能变化；
    
-   重新生成画面可能意外改变声音。
    

正确做法是：

-   云端视频尽量生成无对白画面；
    
-   必要时保留环境音和音效；
    
-   最终旁白始终使用本地声音档案；
    
-   如果云端视频包含不需要的对白，合成时移除或静音；
    
-   本地旁白作为最终主音轨。
    

---

# 十四、`IndexTTS2（声音克隆模型）` 和 `OmniVoice（多语言声音模型）` 怎么分工

建议不要让用户直接理解模型细节，而是创建“声音引擎配置”。

## `IndexTTS2（声音克隆模型）`

更适合作为：

-   中文旁白默认候选；
    
-   有明确参考音色的克隆旁白；
    
-   需要较强情绪表达的短段落；
    
-   中短文本分块生成。
    

官方说明中已经提供情绪控制设计，但官方仓库同时明确写明，标称的精确合成时长控制在发布版本中尚未启用。因此不要根据目标时长要求它直接生成固定秒数音频。

## `OmniVoice（多语言声音模型）`

更适合作为：

-   多语言旁白；
    
-   跨语言声音克隆；
    
-   通过文字描述设计声音；
    
-   需要特殊口音或音高；
    
-   长文本旁白；
    
-   笑声、叹气等非语言表达。
    

官方仓库目前声明支持六百多种语言、声音克隆、声音设计和发音控制。

实际项目中建议提供这些声音策略：

-   中文高相似度；
    
-   中文情绪旁白；
    
-   多语言克隆；
    
-   文字设计声音；
    
-   长文本稳定模式；
    
-   快速预览模式。
    

底层再决定使用 `IndexTTS2（声音克隆模型）` 还是 `OmniVoice（多语言声音模型）`。

---

# 十五、声音档案应该与视觉主体分开

旁白解说类短视频中，画面里的主体通常并不说话。

例如：

-   画面是小猫；
    
-   旁白是成年男性；
    
-   小猫不需要绑定男性声音。
    

所以声音档案应该是项目级独立资源：

-   旁白声音；
    
-   参考音频；
    
-   参考音频文字；
    
-   语言；
    
-   发音词典；
    
-   默认情绪；
    
-   默认语速；
    
-   使用的声音引擎；
    
-   工作流版本；
    
-   声音授权确认。
    

视觉主体可以选择性关联声音档案，但不是必填。

只有在下面这些场景中才需要绑定：

-   多角色对白；
    
-   数字人口播；
    
-   卡通人物说话；
    
-   动物拟人配音；
    
-   系列吉祥物固定声音。
    

---

# 十六、旁白音频必须成为主时间线

旁白解说短视频最稳定的生成顺序不是先生成画面，而是：

1.  生成或导入文案；
    
2.  拆分叙事片段；
    
3.  对每个片段进行语义分块；
    
4.  使用本地声音模型生成音频；
    
5.  使用 `ffprobe（媒体探测工具）` 获取真实时长；
    
6.  必要时做语音强制对齐；
    
7.  根据音频时长决定每个片段需要几个视觉镜头；
    
8.  再生成或选择图片与视频；
    
9.  把视觉镜头分配到旁白时间段；
    
10.  生成字幕；
     
11.  合成背景音乐和最终视频。
     

也就是：

> **音频决定时间，画面适配音频。**

不能反过来让音频强行适配已经生成的固定时长画面。

## 一个例子

某段旁白实际时长是十二秒。

不应该：

-   只放一张图十二秒；
    
-   把五秒视频强行拉伸到十二秒；
    
-   把旁白加速到五秒。
    

应该拆成：

-   第一镜头三点五秒；
    
-   第二镜头四秒；
    
-   第三镜头四点五秒。
    

三个镜头共同覆盖这段旁白。

对于只能生成固定时长视频的供应商，系统应在生成前就根据旁白时长拆镜头，而不是生成后再暴力变速。

---

# 十七、字幕也要来自同一份旁白块契约

每个旁白块保存：

-   原始文本；
    
-   在完整文案中的起止字符位置；
    
-   清洗后的朗读文本；
    
-   实际音频；
    
-   实际时长；
    
-   在主时间线中的开始时间；
    
-   在主时间线中的结束时间；
    
-   词级或句级时间；
    
-   发音修正；
    
-   声音引擎；
    
-   工作流版本；
    
-   音频文件摘要。
    

字幕直接根据这些旁白块生成。

如果声音模型不能输出词级时间，就增加一个本地强制对齐步骤。不能让大语言模型凭感觉估算字幕时间。

# 十九、生成契约必须是供应商无关的

建议短视频内部先生成统一的视觉契约，再转换成具体供应商请求。

视觉契约至少包括：

-   当前视觉镜头编号；
    
-   主要视觉主体；
    
-   次要视觉主体；
    
-   主体身份版本；
    
-   身份锁定；
    
-   可变槽位；
    
-   禁止特征；
    
-   场景；
    
-   道具；
    
-   风格；
    
-   构图；
    
-   景别；
    
-   镜头运动；
    
-   正向提示词；
    
-   负向提示词；
    
-   参考图片及参考角色；
    
-   目标时长；
    
-   目标比例；
    
-   输出规格；
    
-   是否允许原生音频。
    

然后分别转换：

-   `Z-Image（造相模型）` 提示词包；
    
-   `Kling（可灵视频模型）` 请求；
    
-   `Seedance（即梦视频模型）` 请求；
    
-   `Veo（谷歌视频模型）` 请求；
    
-   `Grok Imagine（格罗克视觉生成模型）` 请求。
    

这样更换模型时，不需要重写短视频镜头业务。

# 二十、参考图必须带“角色”，不能只是数组

同一张图片在不同请求中可能承担不同作用：

-   主体身份；
    
-   主体服装；
    
-   主体姿势；
    
-   场景；
    
-   道具；
    
-   视觉风格；
    
-   首帧；
    
-   尾帧。
    

因此短视频生成契约不应继续使用简单的：

`referenceImages（参考图片数组）`

而应使用带语义的参考资源。

供应商适配器负责选择：

-   `Veo（谷歌视频模型）` 最适合发送哪三张；
    
-   `Grok Imagine（格罗克视觉生成模型）` 使用哪张作为视频首帧；
    
-   `Kling（可灵视频模型）` 哪些作为人物或元素参考；
    
-   `Seedance（即梦视频模型）` 如何组织首帧、尾帧和其他参考；
    
-   本地工作流把哪张复制到哪个输入节点。

# 二十一、视觉一致性要形成闭环

生成图片或视频后，建议增加一个视觉语言模型检查步骤。

检查项目包括：

-   主体数量是否正确；
    
-   是否出现错误人物；
    
-   人物脸部是否一致；
    
-   动物物种和花纹是否一致；
    
-   卡通形象配色和比例是否一致；
    
-   标志性配饰是否丢失；
    
-   服装是否符合当前可变槽位；
    
-   风格是否越界；
    
-   场景是否符合镜头要求；
    
-   是否出现禁止文字；
    
-   是否出现多余肢体；
    
-   是否错误替换了画面主体。
    

输出分为：

-   通过；
    
-   警告；
    
-   阻断。
    

失败后的处理顺序建议是：

1.  补强身份锁定提示；
    
2.  更换参考图组合；
    
3.  切换为强制参考工作流；
    
4.  重新生成；
    
5.  仍然失败时交给用户选择。
    

第一版不必追求一个绝对准确的数值分数，可以先提供明确的问题列表和对比图。

# 二十二、资源版本与失效传播必须做清楚

短视频经常只修改一个地方，不应该每次全部重做。

| 修改内容 | 应失效的下游资源 |
| --- | --- |
| 修改文案 | 旁白、字幕、时间线、最终视频 |
| 修改视觉主体版本 | 使用该主体的镜头图片和视频 |
| 修改某个镜头提示词 | 当前镜头媒体及最终视频 |
| 修改声音档案 | 旁白、字幕、时间线、最终视频 |
| 修改旁白音频 | 当前片段时间分配、字幕和最终视频 |
| 修改背景音乐 | 只重新合成最终视频 |
| 修改字幕样式 | 只重新渲染字幕和最终视频 |
| 更换云端视频供应商 | 只重新生成指定镜头及最终视频 |

每个媒体资源都应保存：

-   输入契约摘要；
    
-   视觉主体版本；
    
-   参考资源摘要；
    
-   供应商；
    
-   模型；
    
-   工作流；
    
-   随机种子；
    
-   外部任务编号；
    
-   输出文件摘要；
    
-   成本；
    
-   生成时间；
    
-   父资源版本。

# 二十三、任务队列也需要扩展

当前 `ai-m（新项目）` 任务表主要是简单的等待、运行、完成、失败状态，并保存载荷、结果、错误和重试次数。对于本地推理和云端视频长任务，还缺少外部任务编号、进度、心跳和去重信息。

建议增加：

-   队列类型；
    
-   资源锁；
    
-   外部任务编号；
    
-   当前进度；
    
-   心跳时间；
    
-   开始时间；
    
-   完成时间；
    
-   去重标识；
    
-   取消状态；
    
-   恢复数据；
    
-   供应商成本。
    

队列至少分成：

-   文本任务；
    
-   本地图像显卡任务；
    
-   本地声音显卡任务；
    
-   云端视频任务；
    
-   中央处理器渲染任务。
    

同一张显卡运行 `Z-Image（造相模型）`、`IndexTTS2（声音克隆模型）` 和 `OmniVoice（多语言声音模型）` 时，默认串行执行。

云端视频任务可以按供应商限流并行。

# 二十四、本地推理建议支持多个 `ComfyUI（本地工作流引擎）` 地址

业务层只使用一个本地工作流客户端，但配置层允许多个实例：

-   图像实例；
    
-   声音实例；
    
-   图像修复实例；
    
-   后续的视频增强实例。
    

可以使用同一张显卡，但调度层确保不会同时加载多个大模型。

建议目录：

-   `src/lib/comfyui/（本地工作流基础设施目录）`
    
-   `src/lib/visual-identity/（视觉身份领域目录）`
    
-   `src/lib/short-video/（短视频领域目录）`
    
-   `src/lib/media/（媒体供应商目录）`
    
-   `src/lib/speech/（声音生成目录）`
    
-   `src/lib/timeline/（时间线目录）`
    

原来的：

-   `src/lib/pipeline/（漫剧流水线目录）`
    
-   `src/lib/ai/provider-factory.ts（漫剧供应商工厂文件）`
    

保持原有职责。

短视频新增自己的供应商注册表，不要继续扩大漫剧供应商工厂。

# 二十五、建议把两个项目之间的契约做成通用数据格式

为了保留你在 `Pixelle-Video（短视频生成项目）` 里的大量成果，建议定义几份版本化的 `JSON（结构化数据格式）` 契约：

-   `visual-entity/v1（视觉主体第一版）`

-   `speech-timing/v1（旁白时间第一版）`
    
-   `visual-generation/v1（视觉生成契约第一版）`
    
-   `generation-trace/v1（生成追踪第一版）`
    

然后：

1.  `Pixelle-Video（短视频生成项目）` 可以导出这些契约；
    
2.  `ai-m（新项目）` 可以导入；
    
3.  两个项目使用相同测试样例；
    
4.  `Python（蟒蛇语言）` 和 `TypeScript（类型脚本语言）` 各自实现；
    
5.  不要求两个项目共用运行时代码。
    

这样你的改造成果不会因为重写而全部丢失。

# 二十六、第一版不要同时追求所有模型和所有功能

第一版最合理的完整闭环是：

1.  创建短视频项目；
    
2.  输入主题或固定文案；
    
3.  创建或导入一个视觉主体；
    
4.  建立视觉主体参考包；

6.  使用 `IndexTTS2（声音克隆模型）` 或 `OmniVoice（多语言声音模型）` 生成分段旁白；
    
7.  根据真实音频时长规划视觉镜头；
    
8.  使用本地 `Z-Image（造相模型）` 生成一致性配图；
    
9.  对图片做简单平移与缩放；
    
10.  生成字幕；
     
11.  混合背景音乐；
     
12.  导出完整视频；
     
13.  支持单个图片、音频或镜头重新生成。

-   单镜头 `Kling（可灵视频模型）`；
    
-   单镜头 `Seedance（即梦视频模型）`；
    
-   单镜头 `Veo（谷歌视频模型）`；
    
-   单镜头 `Grok Imagine（格罗克视觉生成模型）`；
    
-   首尾帧视频；
    
-   视觉一致性自动检查；
    
-   系列吉祥物；
